UX direction

Seven decisions behind the screens

An employee opens this app twice a day, often while walking in or out of the building. Every screen is built for a quick, certain action and an answer to "did it count?".

Show eligibility before the action attendance

The Today card reads location as soon as it opens and shows "You're at the office · 42 m" or "850 m away". People learn they can't check in before they try, not from an error afterwards.

One deliberate gesture attendance

Check-in and check-out use slide-to-confirm. A pocket tap can't trigger it and a double tap can't send it twice. The control locks the moment the event is written. With TalkBack or VoiceOver on, it becomes a button with a confirm step.

Sync is always visible, never in the way offline

A pill in the header shows "Synced", "1 waiting", "Syncing" or "Needs attention". Tapping it opens the queue with Sync Now. This replaces a whole Sync tab, so navigation drops to three tabs.

Say exactly what happened feedback

After each action a sheet confirms the time, plus either "Synced with REBS" or "Saved on this phone, sends automatically". A rejected event explains why in plain words and says what to do next.

Offline is a normal state offline

Cached screens load instantly with "Updated 17:40". No blocking spinners after the first launch. Only leave submission is unavailable offline, and the disabled button says why.

Prevent leave errors before reporting them leave

A range calendar blocks past dates and shows existing requests. A live summary shows days requested and the balance left afterwards. Field errors appear only after a field is touched, and server errors land on the field they concern.

Accessible by default all screens

Status always uses an icon plus a word, never colour alone. Tap targets are at least 48 dp. Layouts hold at 130% text size and on 360 dp wide phones. Timers announce changes at most once a minute.

How it fits Stacked

ViewModels expose state only (status, syncSummary, isSubmitting), never controllers or animation values. Views use implicit animations, which need no State. Explicit controllers (slider, tick, pulse, shake) live inside shared widgets in lib/ui/widgets/common/ as StatefulWidgets holding animation state only. That's a documented exception to the stateless shared-widget rule; views stay StackedViews.

Reduce motion

AppMotion.of(context) reads MediaQuery.disableAnimationsOf. When it's on, durations become zero, loops don't start, and the slider still works, it just doesn't spring. Haptics stay.

Testing animated widgets

Loops only run while their state is active, so pumpAndSettle finishes. Widget tests pump with disableAnimations: true. SlideToConfirm gets its own test: one completed drag fires the callback exactly once; a short drag fires nothing.

Not animated on purpose

Page routes use the platform default transition. No staggered list entrances, no hero transitions, no animated numbers on the timer. They'd add time without telling the person anything new.

Main engineering challenge

Offline queue, ordering and idempotency

Every check-in or check-out becomes an event written to the local outbox table before any network call. The UI reads attendance as "server records + my un-rejected local events", so the Today card is correct offline.

outbox
  event_id      TEXT  PK   -- UUID v4, generated once when the slide completes, never regenerated
  type          TEXT       -- CHECK_IN | CHECK_OUT
  work_date     TEXT       -- company-timezone date, e.g. 2026-10-28
  occurred_at   TEXT       -- device UTC timestamp
  lat, lng, accuracy_m REAL
  seq           INTEGER    -- monotonically increasing, defines send order
  status        TEXT       -- PENDING | SYNCING | SYNCED | REJECTED
  attempts      INTEGER
  last_error    TEXT       -- plain-language reason shown in the sync sheet
  dismissed     INTEGER    -- user cleared a rejected event from the list
slide→PENDING→SYNCING→SYNCED /REJECTED · timeout or 5xx →back to PENDING

Duplicate actions

The slider locks once it completes, and the notifier ignores intents while submitting. The policy also checks the outbox: if a CHECK_IN for today exists in any non-rejected state, a second is refused before an event is created.

Ordering

The sync engine sends one event at a time in seq order and stops at the first that stays PENDING. A CHECK_OUT is never sent before its CHECK_IN is SYNCED. A single-flight lock stops manual and automatic syncs from overlapping.

Timeout after server accepted

The retry reuses the same event_id, in the body and as Idempotency-Key. The server stores processed ids; a known id returns the original result, so the client marks it SYNCED and nothing is duplicated.

"Attendance already exists"

A 409 ATTENDANCE_EXISTS for a different event id is a business rejection: mark REJECTED with a plain-language reason, refresh today from the server, and never auto-retry a 4xx.

ResponseClient actionShown as
201 / 200 replayStore server record, refresh todaySynced
409 / 422Save reason, refetch today, stop chain for that dayNeeds attention
timeout / 5xx / no networkattempts++, retry with backoff, same idWaiting

Triggers: app open, app resume, connectivity regained, pull-to-refresh and Sync now. No background work while the app is terminated, as allowed by the brief.

Trust boundary

Checks the server must repeat

The device can be rooted, its clock changed and its GPS mocked. Client checks exist for fast feedback only. The production server has to re-run:

  • One check-in per employee per work day, and check-out only after check-in, computed in the company timezone on the server.
  • Geofence distance from the submitted coordinates, plus rejecting poor accuracy and the Android mock-location flag where available.
  • Timestamp sanity: occurred_at not in the future and within an allowed offline window (for example 24 h), with server receive time stored alongside.
  • Idempotency by event_id, backed by a unique constraint.
  • Leave: start ≥ company today, end ≥ start, reason length, balance, overlap with Pending/Approved, recomputed from server data in one transaction.
  • Identity from the auth token, never from an employee id in the body.
